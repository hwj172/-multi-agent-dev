# 适用边界：投入真实工程前必读

当前 5 个 Agent 的提示词是「**单文件、单轮、无检索**」的设计。它在单文件改动上可用，但**面对多文件服务（如 Spring Cloud 微服务）会直接失效**——不是效果打折，是跑不动。

本文件说明红线在哪、超出后要先补什么。

## 分档

| 阶段 | 场景 | 是否可用 | 需补 |
| --- | --- | --- | --- |
| 当前 | 单文件 / 小任务 | ✅ 可用 | — |
| 中期 | 单服务多文件 | ⚠️ 勉强 | 第 1、2 层 |
| 大项目 | 多服务（Spring Cloud 等） | ❌ **不可用** | 三层全补 |

## 第 1 层：上下文选择

**现状**：`prompts/00-orchestrator.md` 的 fix 阶段要求「只传与问题相关的文件」，但**由谁判定"相关"没有机制**，实际依赖 Orchestrator 的模型自行判断。规模一大必然挑错，Coder 就是在缺上下文的盲修。

**红线**：同一份提示词里的「单次 `input` 尽量不超过约 8000 token」这条约束，**在单服务级别即告失效**——一个 Controller + Service + Feign 客户端 + 配置类轻易超过 3 万 token。

**需要**：代码检索层。依赖图 / AST 切片 / 向量召回，把"相关文件"从口头约束变成可计算的结果。

## 第 2 层：变更表达（整文件覆盖 → diff/patch）

**现状**：Coder 输出 `{"files":[{"path":…, "code":"完整文件内容"}]}`，即整文件覆写。

**风险**：这是**单点全损**设计，两个失效模式都会实际发生：

- 输出超过 `max_tokens` 被截断 → 整份响应报废（实测 Reviewer 和 Tester 都触发过）
- JSON 字符串中一处转义错误（引号、反斜杠、换行）→ 整份响应不可解析，**且没有任何增量恢复手段**

Python 玩具函数只有几十行，看不出来。Java 文件 300–800 行是常态，一个功能动 10 个文件时，转义压测就是上线的第一课。

**需要**：改为输出 diff/patch，而非整文件。

## 第 3 层：编译验证

**现状**：Tester 只输出测试文件与 `run_command`，流水线本身**不做编译/构建验证**。

**风险**：

- Python 下 `pytest` 直接可跑；**Java 不行**——生成的 JUnit 测试需与项目的 Maven/Gradle 构建、依赖、Spring 上下文一致，否则语法正确但编译不过或容器起不来，产出等同废纸。
- 更要紧的是：**类型/API 兼容性的判定权不该给 LLM**。实测 Reviewer 会用错误的理由（「`__str__` 能保证字符串拼接正常工作」——实测不能，`"a" + obj` 抛 `TypeError`）为一处真实的破坏性变更放行。把模块级常量从 `str` 改成自定义对象这类改动，`mypy`/`javac` 会直接报错，而模型会自信地判它通过。

**需要**：接入项目实际的构建系统执行编译与测试；类型/API 兼容性问题以编译器 / 类型检查器（`javac`、`mypy`、`pyright`）的结论为准，Reviewer 的判断仅作参考。

## 成本与延迟的量级

- 玩具级任务实测约 **$0.21/任务**。
- 按单服务级别估算（约 30 万 token 输入、Reviewer 3 轮），**单任务约 $2–5**（估算值，未实测，按实际规模折算）。
- Reviewer 开 thinking 时单次审查实测 184s，大输入下更久。3 轮修复回路意味着单任务从分钟级到十分钟级。

**当前设计不适合交互式场景，只适合异步批处理。**

## 一个容易被忽视的盲区：修复轮次本身

流水线的修复回路（`needs_fix → Coder 修复 → 复审`）里，**修复这一轮是无人审查的**。Coder 修 A 的时候顺手弄坏 B，只要 A 被修好、B 不在上次的 issues 清单里，就会一路绿灯。

`prompts/03-reviewer.md` 里已经补了对应规则（复审须检查本轮改动是否引入新问题），但**这条规则在类型/API 层面的可靠性不足**——见第 3 层。所以在接入编译器之前，修复轮次的产物仍然需要人工抽查。

## 落地顺序建议

别一步到位。按使用规模逐层补：

1. **现在**：单文件 / 小任务，现状够用。
2. **过渡到单服务**：先补 diff 输出（成本最低、收益最直接），再补上下文检索。
3. **多服务工程**：三层全补之后，才谈得上把它接进真实的 Spring Cloud 项目。
